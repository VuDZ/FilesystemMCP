# Regression tests FilesystemMcp

Отдельный xUnit-проект на .NET 10, включён в FilesystemMCP.sln. Покрывает воспроизведения FS-01…FS-13 и контрольные Unicode/stdio/hash сценарии. [Спецификации и backlog](../docs/README.md).

## Статус

FS-01 реализован по пользовательскому override (default true, external links через workspace route) и принят независимым ревью в третьем раунде (версия 1.2.0). Его проверки перенесены в Baseline и расширены до 38 cases. FS-02 принят независимым ревью в первом раунде (версия 1.3.0); его 45 cases находятся в Baseline. FS-03 принят независимым ревью в первом раунде (версия 1.4.0); его 60 cases находятся в Baseline. FS-04 принят независимым ревью (версия 1.5.0; исходно в первом раунде, затем исправлены замечания ревью и подтверждено в раундах 2–3); его 25 cases находятся в Baseline (14 исходных + 11 регрессионных после исправления шести дефектов второго раунда). FS-05 реализован в версии 1.6.0 и принят независимым ревью (в первом раунде подняты замечания, они исправлены и подтверждены в раундах 2–3); его 28 cases находятся в Baseline: четыре исходных `ToolErrorsTests` (два исправленных дефекта `-32602` и минимальный FS-04 prerequisite `file_not_found`), матрица кодов и Windows HResult-строк, `details`/retryable, correlation id для экологического дефекта (инъекция через barrier protected host) и для `ERROR_DIRECTORY`, pathological-regex `resource_limit`, недоступный logger, no-duplicate-response и self-check проверки на sensitive content. FS-08 реализован в версии 1.9.0: `Spec=FS-08` — 75 cases, все в Baseline, все проходят на Windows PowerShell 5.1 и PowerShell 7 там, где он есть (см. ниже); оба прежних KnownDefect-случая закрыты измеренно, а не предположением, а независимое адверсариальное ревью трёх раундов и верификация четвёртого дали 24 замечания, закрытых в коде. Status=KnownDefect означает проверку **желаемого исправленного поведения**, а не ожидание ошибочного результата. Эти тесты активны и не skipped, и все они действительно падают: 23 cases, 0 passes (FS-09…FS-13; FS-06 принят независимым ревью во втором раунде, 20 cases в Baseline). Полный запуск сейчас намеренно красный; passing Baseline не означает полной исправности сервера.

CLI `allowSymLinks` проверяется unit и stdio startup tests. `logDirectory` (FS-06) реализован и проверяется startup- и stdio-тестами. Бюджеты FS-07 реализованы в версии 1.8.0 и проверяются четырьмя классами — `ResourceBudgetsTests` (43), `SearchBudgetTests` (16), `TransportBudgetTests` (26) и `RequestDeadlineTests` (1), всего 86 cases (см. матрицу ниже); соответствующие KnownDefect-случаи сняты.

После исправления пункта перенести проходящие проверки в Status=Baseline, дополнить матрицу приёмки из спеки и выполнить весь проект без фильтра. Не подменять failing tests проверками старого дефектного поведения.

## Запуск из корня репозитория

```powershell
dotnet restore FilesystemMcp/FilesystemMcp.Tests/FilesystemMcp.Tests.csproj -p:PublishAot=false -p:PublishTrimmed=false
dotnet build FilesystemMcp/FilesystemMCP.sln --no-restore -p:PublishAot=false -p:PublishTrimmed=false

# Зелёные контрольные сценарии
dotnet test FilesystemMcp/FilesystemMcp.Tests/FilesystemMcp.Tests.csproj --no-build --no-restore -p:PublishAot=false -p:PublishTrimmed=false --filter 'Status=Baseline'

# Известные дефекты: текущий exit code 1 ожидаем и требует анализа результатов
dotnet test FilesystemMcp/FilesystemMcp.Tests/FilesystemMcp.Tests.csproj --no-build --no-restore -p:PublishAot=false -p:PublishTrimmed=false --filter 'Status=KnownDefect'

# Один пункт / полный целевой gate
dotnet test FilesystemMcp/FilesystemMcp.Tests/FilesystemMcp.Tests.csproj --no-build --no-restore --filter 'Spec=FS-01'
dotnet test FilesystemMcp/FilesystemMcp.Tests/FilesystemMcp.Tests.csproj --no-build --no-restore --logger 'trx;LogFileName=all.trx'
```

NuGet versions согласованы с существующим тестовым проектом репозитория. Production ProjectReference отключает AOT/trim для unit-тестов; build/publish production properties остаются прежними. Compile exclusion и InternalsVisibleTo в production csproj нужны для отделения тестов и доступа к internal API.

## Покрытие

Все числа измерены реальными прогонами на Windows, SDK 10.0.401 / runtime 10.0.12, Debug, `--no-build`: `--filter 'Status=Baseline'`, `--filter 'Status=KnownDefect'`, `--filter 'Spec=FS-XX'` и полный прогон без фильтра. До правки FS-07: Baseline 228 cases (220 passed, 8 skipped, 0 failed), KnownDefect 28 cases. Изменения матрицы: два исходных `ResourceBudgetsTests` переведены из KnownDefect в Baseline и расширены; добавлены `SearchBudgetTests` (16), `TransportBudgetTests` (26) и `RequestDeadlineTests` (1), а также 18 регрессионных cases четырёх дефектов независимого ревью (`ResourceBudgetsTests` +2, `TransportBudgetTests` +14, `SearchBudgetTests` +2) — FS-07 даёт 86 cases в Baseline и ни одного failing Baseline. Регрессии четырёх дефектов: (1) `operationTimeoutMs` выше `4294967294` — startup-отказ (`Startup failed:`) с пустым stdout, а граница `4294967294` и значения 1/2/2147483647/86400000 по-прежнему отвечают initialize + ping + `tools/call` (проверяется именно получение кадра, а не его форма; `long.MaxValue` измеренно тоже отвергается — `MaxOperationTimeoutMs` это жёсткая граница для всего диапазона выше неё); (2) при малом `maxResponseChars` каждый доставленный кадр — целый JSON с сохранённым `id`, не превышающий бюджет, когда бюджет не ниже измеренной длины минимального кадра (97 символов для 4-значного id), с обеими ветками: bounded `resource_limit`-конверт для `tools/call` и JSON-RPC error `-32603 "Response exceeds maxResponseChars"` для `tools/list` и `-32601` с 4000-символьным именем метода; (3) peer `notifications/cancelled` в последней доле бюджета → `isError:true`/`cancelled` через production-дискриминатор (`SearchTool.IsDeadlineExceeded` не задан), а реально истёкший `--operationTimeoutMs` → partial result `isError:false` с `truncation_reason:"operation_timeout"`; (4) полное чтение файла отклоняется во время чтения (`textLimit`), включая `allow_large_read`, с доказательством по числу байт, запрошенных у потока, и по аллокации. KnownDefect 28 → 25: снят FS-13 `MalformedJsonReturnsParseErrorWithExplicitNullId` (следствие явного `id:null` у unattributed отказа), при этом `UnifiedApiTests.CustomRpcMethodsAreRejectedInsteadOfExecutingDivergentOrStubOperations` — одна `[Theory]`, где теперь падают все шесть InlineData-кейсов (измерено 6 cases, 0 passed, 6 failed; ранее — 5 из 6): с FS-07 legacy direct RPC методы вызывают тот же registered tool, а не расходятся с ним. Это осознанное изменение наблюдаемого поведения FS-12 (методы удаляются его реализацией), а не регрессия Baseline. Классы FS-07: `ResourceBudgetsTests` (43), `SearchBudgetTests` (16), `TransportBudgetTests` (26). Fixtures малого размера: 64 MiB и 2 MiB сценарии используют генерирующий `Stream`, реальные большие файлы не создаются. Синхронизация только через именованные pipe-barrier'ы protected TestHost (`ToolExecutionGate` + `TestHooks.ToolExecutionBarrier`); таймеры — только watchdog'и. Никакие sleeps не синхронизируют concurrency/observer assertions. Observer открывает файл с ReadWrite/Delete sharing и проверяет только full old/new bytes; Windows publication использует FileRenameInformationEx POSIX semantics. Temp cleanup не затрагивает неизвестный `.filesystemmcp-unknown.tmp` и temp активного другого writer. Crash recovery/scanning чужих temp не добавлены.
## Окружение и изоляция

- Fixtures создаются только под temp/filesystemmcp-tests-<guid>. Внешний относительно workspace файл тоже лежит в этом sandbox. Настоящие repo files/user configs не редактируются.
- FS-06: каталог диагностики по умолчанию — пользовательский (`%LOCALAPPDATA%\FilesystemMCP\logs`), поэтому тесты логов задают `--logDirectory` внутри своего sandbox и не пишут в общий каталог. Живой лог читается только с `FileShare.ReadWrite | FileShare.Delete`: `File.ReadAllText` открывает файл с `FileShare.Read` и падает, пока writer держит его, что выглядело бы как отсутствие диагностики.
- FS-06: недоступность stderr нельзя воспроизвести закрытым пайпом (Windows-рантайм считает `ERROR_NO_DATA`/`BROKEN_PIPE` успехом записи), поэтому эта ветка проверяется инъекцией `McpLogger.ErrorWriter`/`FailNextWrite`; закрытие читающего конца stderr в harness не используется, так как `DrainStderrAsync` в этом случае не завершается.
- Cleanup проверяет абсолютную границу temp, удаляет собственные junction entries без следования целям и затем собственный sandbox.
- WindowsFact явно skipped вне Windows. Junction создаётся PowerShell без symlink privileges/Developer Mode. Ошибка создания junction — fixture failure, не тихий skip.
- SymlinkFact делает capability probe и явно сообщает skip, если OS/account не разрешает file/directory symlinks. Linux/macOS тесты используют реальные symlinks и `openat`; они не превращены в Windows-only tests. Cleanup обходит sandbox по entries и удаляет reparse entries без следования, включая dangling links и ссылки, перемещённые fault hooks.
- ShortNameFact делает Windows 8.3 capability probe; при отсутствии aliases явно skipped. Junction target validation использует физический handle path и сохраняет границу собственного sandbox, включая short aliases. Nested-drive regression задаёт cwd дочернего protected host внутри sandbox; global cwd не меняется.
- Installer/junction tests требуют PowerShell: Windows PowerShell 5.1 по умолчанию на Windows, pwsh на других OS. FILESYSTEM_MCP_TEST_POWERSHELL задаёт иной executable. Отсутствие PowerShell — явная ошибка окружения.
- FS-08: матрица всегда прогоняет обе доступные линии: 67 cases идут на shell по умолчанию (Windows PowerShell 5.1 на Windows), а `PwshFactAttribute` добавляет 8 cases на PowerShell 7 и skip'ает их с причиной, если `pwsh` нет в `PATH`; FILESYSTEM_MCP_TEST_POWERSHELL намеренно не влияет на эту линию, потому что переопределяет *основной* shell, а он не обязательно pwsh. Все fixtures установщика живут в своём `Sandbox` под temp; настоящий пользовательский `opencode.json`/`AGENTS.md` не читается и не пишется. `-AllowSymLinks` приходится передавать строкой (значение через пробел не биндится в `[bool]` ни в 5.1, ни в 7), поэтому случаи используют `-AllowSymLinks:false` и `-AllowSymLinks false`; обе формы проверены.
- Protocol tests запускают настоящий process, читают UTF-8 frames, постоянно дренируют bounded stderr и используют watchdog. Свой process завершается принудительно, если сам не выходит; чужие процессы не затрагиваются.
- По умолчанию отдельный FilesystemMcp.TestHost запускает настоящий production entry point в своём managed процессе. Host перехватывает escaping exceptions, пишет исходную ошибку в stderr и возвращает exit code 1 без выдуманного MCP ответа. В Windows он также задаёт SEM_NOGPFAULTERRORBOX внутри дочернего процесса после CLR startup. Настройка родителя оказалась недостаточной; CreateNoWindow скрывает только console. [Microsoft SetErrorMode](https://learn.microsoft.com/en-us/windows/win32/api/errhandlingapi/nf-errhandlingapi-seterrormode).
- TestHost не меняет protocol/tool реализацию и сохраняет InvariantGlobalization/JSON runtime settings сервера. Infrastructure self-test использует одиночный аргумент --test-host-crash-probe. Только protected TestHost может подключить internal atomic-write dependency к named-pipe barriers через свои FS_TEST_ATOMIC_PIPE/FS_TEST_ATOMIC_POINTS environment variables; production entry point не читает их и не имеет fault CLI/API. Глобальные Windows/registry настройки не меняются.
- Unit testhost не включает InvariantGlobalization глобально; stdio server сохраняет production runtime settings. Unit encoding fixtures не зависят от culture.

## Проверка опубликованного Native AOT сервера

```powershell
$env:FILESYSTEM_MCP_TEST_SERVER = 'C:\absolute\publish\FilesystemMCP.exe'
dotnet test FilesystemMcp/FilesystemMcp.Tests/FilesystemMcp.Tests.csproj --no-build --no-restore
Remove-Item Env:FILESYSTEM_MCP_TEST_SERVER
```

Variable указывает на реальный абсолютный путь опубликованного binary. Замена затрагивает обычные process tests; unit tests используют managed ProjectReference. Преднамеренно аварийный logger test и process-launch control всегда используют защищённый managed TestHost, даже с внешним binary: автоматический crash native binary на рабочем desktop в этой suite не выполняется. Installer использует заданный binary как config argument. AOT publish и другие OS в текущем snapshot не проверены; это будущий CI gate.
