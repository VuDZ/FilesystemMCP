# FS-11: Пустая замена и whitespace snippets

Приоритет: P2. Источник: ReplaceInFileTool.GetRequiredString.

Статус: выполнено.

Версия реализации: **1.11.0**. Независимое ревью: раунд 1 нашёл расхождения parity schema/runtime и завышенные заявления о покрытии — они правились; раунд 2 нашёл, что parity-фикс `target_snippet` был внесён неверно (schema запрещала whitespace-only цель, тогда как норма и рантайм её требуют) — исправлено здесь: `pattern` у `target_snippet` снят, у `original_hash` оставлен, разница объяснена в разделе реализации; раунд 2 дополнительно уточнил перечень вызовов серверного кейса, список дискриминирующих snippet-кейсов и покрытие удаления всего содержимого; раунд 3 подтвердил норму и числа, но нашёл, что parity-утверждение ничем не проверялось, что классы пробельных символов у `pattern` и у `string.IsNullOrWhiteSpace` расходятся на U+0085/U+FEFF, что перечень дискриминирующих snippet-кейсов неполон и что часть граничных ассертов тавтологичны — по итогам добавлен кейс parity published schema против runtime, уточнены формулировки контракта, происхождение границы `additionalProperties` (FS-12, docs/12:21), перечень дискриминирующих кейсов и арифметика состава. По коду FS-11 функциональных дефектов ревью не заявляло. Открыто вне FS-11: внешний тайминговый дефект FS-07 `SearchBudgetTests.SearchThatGenuinelyExceedsTheOperationTimeoutReturnsAPartialResult` (см. раздел ниже) — его исправление отдельной работой в эту спеку не входит. Приёмка (Windows, SDK 10.0.401, Debug): managed build `-m:1 -p:UseSharedCompilation=false -p:PublishAot=false -p:PublishTrimmed=false --no-incremental` — 0 warnings/errors; `Spec=FS-11` — 44 cases: 44 passed, 0 failed, 0 skipped; `Status=Baseline` — 454 cases: 446 passed, 0 failed, 8 skipped; `Status=KnownDefect` — 15 cases: 15 failed (прежние FS-10/12/13); полный прогон — 469 cases: 446 passed, 15 failed, 8 skipped, где все 15 падений — KnownDefect FS-10/12/13 (454 Baseline + 15 KnownDefect = 469). Снимки: `../FilesystemMcp.Tests/TestResults/fs11-acceptance-44.trx` (полный прогон, FS-11 внутри 44/44), `fs11-acceptance-44-baseline.trx` (454 — 446 passed, 0 failed, 8 skipped) и `fs11-acceptance-44-knowndefect.trx` (15 — 15 failed); прежние `fs11-full.trx`/`fs11-full-2.trx` относятся к матрицам 468/463 cases и оставлены историей.

## Дефект

Schema разрешает replacement_snippet="", сервис умеет deletion, но tool отвергает пустой/whitespace text через IsNullOrWhiteSpace. Невозможно удалить фрагмент или заменить на перенос/пробелы.

## Контракт

- replacement_snippet обязательно присутствует и имеет JSON string type; разрешены "", " ", "\n", "\t" и любые combinations.
- target_snippet обязателен, string type и непустой по Length; whitespace-only допустим и сопоставляется точно.
- original_hash обязателен, непустой (whitespace-only значение не является хешем и отвергается как аргумент — уточнение 1.11.0, см. раздел реализации); ведущие/конечные whitespace не trim автоматически. path сохраняет общий contract.
- Missing/null/wrong type → -32602 через FS-05; не подставлять empty вместо отсутствующего поля.
- Delete может удалить всё содержимое, оставив корректный пустой файл в исходном encoding/BOM contract FS-03.
- Нормализация EOL для matching остаётся; поиск первого точного совпадения сохраняется. Не добавлять change-all/ambiguity rejection в этом пункте.
- Новый hash и snippet корректны для empty/whitespace итогового текста. BuildSnippet использует фактическую позицию правки, а не поиск пустого search token.

## Реализация (1.11.0)

- Schema и runtime согласованы для трёх текстовых аргументов. `target_snippet` — `"type": "string", "minLength": 1` (без `pattern`): непустой по Length, при этом whitespace-only цель schema разрешает — она допустима и сопоставляется буквально (Baseline-кейс `("a  b", "  ", "_", "a_b")`). `replacement_snippet` — `"type": "string"` без ограничений, то есть допускает `""`. `original_hash` — `"type": "string", "minLength": 1` **и** `pattern: "\\S"` (JSON Schema ищет подстроку, поэтому `\S` означает «есть хотя бы один непробельный символ»): whitespace-only хеш не может совпасть ни с одним дайджестом, поэтому он отвергается уже как аргумент. Асимметрия с `target_snippet` намеренная и повторяет runtime: `RequiredText.NonEmpty` через `string.IsNullOrEmpty` (Length) против `RequiredText.NonWhitespace` через `string.IsNullOrWhiteSpace`, плюс `RequiredText.Any` для замены. Отсутствующий аргумент, JSON `null` и не-строка дают одно и то же `ArgumentException` → `-32602` через FS-05; пустая подстановка вместо отсутствующего поля не делается; ни один аргумент не trim'ается.
- Известные границы parity, не входящие в FS-11: `additionalProperties: false` объявлен в schema, но runtime лишние свойства игнорирует — нормативное требование «Validate additionalProperties и типы на сервере» принадлежит FS-12 (docs/12:21), а не FS-05; `path`/`filePath`/`file_path` не описаны через `anyOf` и остаются общим контрактом `ToolArguments.GetRequiredPath` — требование «schema требует хотя бы один из алиасов» тоже принадлежит FS-12 (docs/12:20). Ещё одна граница внутри самой FS-11: `pattern: "\S"` у `original_hash` — выражение ECMA-262, тогда как runtime использует .NET `string.IsNullOrWhiteSpace`; классы пробельных символов расходятся на U+0085 (schema считает символ непробельным, runtime — пробельным) и U+FEFF (наоборот). Оба расхождения видит только клиент, валидирующий `inputSchema`; в обоих случаях исход — отказ, поэтому runtime не менялся, а граница зафиксирована здесь (проверка parity в `EmptyReplacementTests.PublishedSchemaMatchesTheRuntimeRulesForTheTextArguments` фиксирует сам `pattern` и его поведение на ASCII-пробелах).
- Positional anchor. `TextDocument.Replace` возвращает `(Canonical, Bytes, Index)`, где `Index` — offset первого точного совпадения в LF-нормализованном тексте (он же начало правки в результате). `AtomicWriteResult` получил `int? ReplaceIndex` (`null` у whole-text записи `WriteTextAsync`), `FileService.ReplaceInFileAsync` — третий элемент кортежа `(NewText, NewHash, ReplaceIndex)`, `BuildSnippet(text, replaceIndex)` строит окно вокруг этой позиции по прежней формуле (`start = max(0, anchor − MaxSnippetLength/2)`, `length = min(MaxSnippetLength, len − start)`), а при `text.Length <= MaxSnippetLength` по-прежнему возвращает весь текст. До 1.11.0 позиция искалась как `IndexOf(replacement)` в результате: для удаления это 0 (окно описывало начало файла), а при повторе текста замены в файле окно уезжало к первому вхождению. Границы: правка в начале (окно от 0), в конце (хвост короче окна), пустой результат (пустой snippet), длина результата ровно `MaxSnippetLength` (весь текст) и `+1` (окно).
- Сохранено без изменений: нормализация EOL для matching, поиск первого точного совпадения (change-all/ambiguity rejection не добавлялись), формат ответа `status`/`new_hash`/`snippet`, коды FS-05, кодировка/BOM результата — включая корректный пустой файл (только BOM, если он был) после удаления всего содержимого (FS-03).
- Backlog: expected_match_count и позиционный anchor как параметр запроса (B-10) не реализованы; snippet остаётся ответной диагностикой инструмента.

## Приёмка

EmptyReplacementTests: delete middle, delete all, replacement whitespace, whitespace-only target и SHA256 итогового normalized текста. Invalid empty target и отсутствующий replacement — контрольные tests.

Реализовано в 1.11.0, дополнено по находкам раундов 1–3 ревью. Состав 44 cases: 4 кейса `EmptyAndWhitespaceSnippetsAreValid` (прежние KnownDefect — переведены в Baseline) и 2 прежних Baseline-контроля; 16 кейсов прямой теории wrong types/null/отсутствующего поля/blank hash — по числу, объекту, массиву, `null` и отсутствию для каждого из трёх текстовых аргументов, всегда без записи и без temp; 1 серверный кейс — те же формы как `-32602` (17 вызовов: по пять форм для `target_snippet` и `replacement_snippet`, плюс число/объект/массив/`null`/отсутствие/whitespace-only для `original_hash` и пустой `target_snippet`) плюс контроль отсутствия записи и temp; 1 кейс — parity published schema против runtime (`PublishedSchemaMatchesTheRuntimeRulesForTheTextArguments`: `replacement_snippet` без `minLength`/`pattern`, `target_snippet` только `minLength: 1`, `original_hash` `minLength: 1` + `pattern: "\S"`, плюс поведение тех же трёх форм по проводу — whitespace-only цель даёт `target_not_found`, а не `-32602`, whitespace-only хеш и пустая цель дают `-32602`); 1 кейс — hash с ведущим/хвостовым пробелом, табом и CRLF не trim'ается (`hash_conflict`), whitespace-only хеш и пустая цель — аргументный отказ без записи; 2 кейса — newline replacement в CRLF-файле и в UTF-16(BOM) файле; удаление всего содержимого параметризовано по шести кодировкам FS-03 (`utf8`, `utf8bom`, `utf16le`, `utf16be`, `utf32le`, `utf32be`) — на диске ноль байт для UTF-8 без BOM и ровно исходный BOM для пяти BOM-кодировок, повторное чтение даёт `""` и SHA256 пустой строки (6 кейсов); 2 кейса — `"\n"` берёт первое совпадение, terminal delimiter удаляется; 1 кейс — несколько одинаковых targets правит первое (и при замене, и при удалении); 1 кейс — удаление всего содержимого UTF-8 (пустой файл, hash пустой строки, пустой snippet); 7 snippet-кейсов — удаление, повтор текста замены, смещение внутри головы длинного результата, конец результата, ровно 400 (сохранённое поведение), 401 в двух положениях правки и CRLF-файл, где canonical-offset отличается от raw-offset. Дискриминирующими относительно алгоритма 1.10.0 (`IndexOf(replacementSnippet)`) являются: удаление (`SnippetForDeletionIsAnchoredAtTheDeletedRange`), повтор текста замены (`SnippetIsAnchoredAtTheEditNotAtAnEarlierOccurrenceOfTheReplacement`), вторая фаза `SnippetAtTheStartOfALongResultIsTheLeadingWindow` (смещённая голова; её первая фаза при правке в offset 0 совпадает у обеих реализаций и это признано в комментарии теста), `SnippetAtTheEndOfALongResultKeepsTheTail` (старое окно дало бы 400 символов головы, новый якорь даёт 200 символов хвоста), обе фазы `SnippetOneCharacterOverMaxSnippetLengthIsClippedToTheWindow` (401 при правке в конце и 401 при правке на offset 201) и `SnippetInCrlfFileUsesTheCanonicalOffsetOfTheEdit`. Не различает реализации ровно один кейс — `SnippetAtExactlyMaxSnippetLengthIsTheWholeResult` (при `len <= 400` обе версии возвращают весь текст); он остаётся контролем сохранённого поведения из контракта, и это записано в самом тесте. Проверяются `new_hash` (SHA256 нормализованного текста), `snippet`, а где нужно — байты/кодировка/BOM. Expected match count/позиционный anchor — backlog (B-10).

Добавить: wrong types/null, newline replacement в CRLF/UTF-16, удаление terminal delimiter, длинный файл и snippet около фактической правки, несколько одинаковых targets (сохранить first-match) — весь список закрыт в 1.11.0 (перечень выше). Expected match count/позиционный anchor — backlog.

## Открыто вне FS-11: тайминговый случай FS-07 (не закрыт)

`SearchBudgetTests.SearchThatGenuinelyExceedsTheOperationTimeoutReturnsAPartialResult` (Baseline, `SearchBudgetTests.cs:492-511`) создаёт ворклоад из 2000 файлов (`WriteSearchWorkload(sandbox, 2000)`, `:497`) и запускает сервер с `--operationTimeoutMs=2000`, рассчитывая, что обход займёт «несколько секунд» (комментарии `:478-491`, `:513-519`: около 2 мс на файл). Когда обход укладывается в бюджет, поиск завершается сам, в успешном ответе нет `truncation_reason` и тест падает `KeyNotFoundException` на `:504` — форма отказа это прямо доказывает, потому что ветка частичного результата по дедлайну всегда добавляет `truncation_reason`. Измерено на одной и той же сборке: изолированный прогон — 2× passed (мои замеры) и 2× failed (`Total 1 · Passed 0 · Failed 1`, замеры ревьюера); `Status=Baseline` — 0 failed (финальный снимок: 454/446/0/8) и 1 failed (замер ревьюера на прежней матрице 448/439/1/8); в полном прогоне — 0 failed в финальном снимке (469/446/15/8, то есть ровно KnownDefect) и 1 failed в прогоне оркестратора на матрице 468 cases (445 passed, 16 failed, 8 skipped). То есть результат зависит от того, укладывается ли обход в двухсекундный бюджет, а не от нагрузки. К FS-11 это не относится: диф спеки не касается `SearchTool.cs`, `RequestDeadline.cs` и `FileContentReader.cs` (файлы идентичны HEAD), а фикстуры теста создаются прямыми записями; причина — хрупкое допущение самого теста о скорости окружения. Исправление допущения — отдельная работа вне FS-11; в этой спеке дефект не закрывается.

Зависимости: FS-02/03/05/12. Schema и runtime validator обновляются вместе.
