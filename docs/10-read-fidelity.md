# FS-10: Точное чтение строк и явное truncation

Приоритет: P2. Источники: FileTextHelper.ExtractRequestedContent, FileService.ReadFileAsync, ReadFileResult.

Статус: выполнено.

Версия реализации: **1.12.0**. Приёмка (Windows, SDK 10.0.401, Debug): managed build `-m:1 -p:UseSharedCompilation=false -p:PublishAot=false -p:PublishTrimmed=false --no-incremental` — 0 warnings/errors; `Spec=FS-10` — 34 cases: 34 passed, 0 failed, 0 skipped; `Status=Baseline` — 487 cases: 479 passed, 0 failed, 8 skipped; `Status=KnownDefect` — 10 cases: 10 failed (все — прежние FS-12/13); полный прогон — 497 cases: 479 passed, 10 failed, 8 skipped, где падающий набор совпадает с KnownDefect-фильтром (FS-12 ×8 + FS-13 ×2), ни одного падения от FS-10. Финальное ревью нашло дефект первой редакции 1.12.0: закрывающий LF выбранной строки не входил в проверку `textLimit` внутри `Emit`, поэтому отказ по бюджету из-за одного этого LF случался только в `OnScanCompleted` — после дочитывания всего хвоста файла; исправлено тем же 1.12.0: +1 на закрывающий LF считается уже в `Emit`, и отказ обрывает чтение немедленно (кейс `ClosingLfOverTheResponseBudgetStopsTheReadImmediately`, обе формы — range и prefix `allow_large_read`). Внешний тайминговый дефект FS-07 `SearchBudgetTests.SearchThatGenuinelyExceedsTheOperationTimeoutReturnsAPartialResult` упал в первом Baseline-прогоне после этого фикса и прошёл изолированно, в повторном Baseline и в финальном полном прогоне — это хрупкое допущение самого теста о скорости окружения, вне FS-10 (см. [11-empty-replacement.md](11-empty-replacement.md)). До правки FS-10: Baseline 454 cases (446 passed, 8 skipped), KnownDefect 15 (FS-10 ×5 + FS-12 ×8 + FS-13 ×2), весь проект 469 cases. Изменение trailing delimiter в `text` диапазонных чтений — документируемая коррекция контракта (см. ниже): семь существующих Baseline-тестов других спек (FS-07 ×5, FS-03 ×1, FS-09 ×1), ожидавших прежний обрезанный текст, обновлены вместе с реализацией.

## Дефект

selected.Length теряет начальные пустые строки. Text теряет trailing newline. Custom max_lines возвращает prefix без признака truncation, хотя hash описывает весь файл.

## Контракт

- Полный read возвращает полный normalized LF text, включая leading blank lines и terminal LF. Empty file → text="", total_lines=0. Terminal LF не добавляет фиктивную новую строку: "\n" содержит одну пустую строку, "a\n" — одну строку.
- Range 1-based включителен. Между выбранными строками LF, а LF после последней выбранной строки возвращается, если этот delimiter присутствовал в исходном normalized тексте. Начальные пустые строки диапазона сохраняются.
- start_line за EOF → пустой диапазон и metadata; end_line за EOF clamp к последней доступной строке. Invalid отрицательный/обратный range — ошибка аргументов.
- md5/sha256 всегда описывают полный normalized decoded файл без BOM; никогда не вычислять hash лишь по selection.
- Read result дополняется total_lines, start_line, end_line (null для empty selection), truncated, has_more. start/end описывают фактически возвращённый диапазон. has_more означает наличие строк после возвращённой end_line; truncated означает срабатывание cap, а не сам запрос range.
- Сохранить default full-read rejection >1000 и explicit range limit; allow_large_read+max_lines — допускаемый prefix cap с truncated=true при превышении. max_lines при allow_large_read=false — invalid arguments вместо молчаливого игнорирования.
- Когда ответ превысил chars budget, возвращать валидный bounded result с metadata или resource_limit, не скрыто обрезанный JSON. **FS-07 выбирает из этой альтернативы:** при превышении бюджета `maxResponseChars` полное чтение возвращает `resource_limit` (отказ), а не усечённый успех с metadata — потому что частичный текст без признака неполноты расходится с требованием полного hash выше, а `truncated` у этой операции означает срабатывание prefix cap, не бюджета. Отказ приходит **во время** чтения, не дожидаясь конца сканирования.
- Правило бюджета распространяется на **все** формы чтения, а не только на полное: range и prefix `allow_large_read` при превышении `maxResponseChars` тоже дают `resource_limit`. Выбранный текст обязан уложиться в бюджет; это сужение первоначальной формулировки, где выбор был описан для полного чтения.
- Порядок лимитов чтения (FS-07 R1): `maxFileBytes` → `maxLineChars` → `maxResponseChars` → guard-ы строк 1000/50000. Раньше по номеру — раньше по исходу. Отказ на любом из первых трёх шагов **прекращает сканирование**: дочитывать файл незачем, потому что отказ не несёт ни текста, ни hash, а ожидание только расходует бюджет. Поэтому guard-ы 1000/50000 применяются лишь к чтениям, дошедшим до конца, и конкуренция «бюджет против guard'а» на одном файле разрешается номером шага: клиент видит `resource_limit` с причиной того шага, который сработал первым.

## Реализация (1.12.0)

- Отбор строк живёт в стриминговом `FileContentReader.CanonicalSink` и в эталонном `FileTextHelper.ExtractRequestedContent` (парность удержана тестами FS-07 `StreamingReaderMatchesTheAcceptedReference`/`PrefixCapTruncatesLikeTheAcceptedReference`). Решение о разделителе больше не выглядит на непустоту буфера (`selected.Length > 0` терял первую пустую выбранную строку), а отслеживает факт «строка уже выбрана»: выбранная пустая строка занимает своё место, следующая получает свой `\n`. Delimiter, закрывший последнюю выбранную строку в исходном normalized тексте, дописывается после конца сканирования (`CanonicalSink.OnScanCompleted`): только конец файла доказывает, что закрывающего delimiter'а не было. Поэтому range и prefix cap — точная подстрока canonical текста, а полный read возвращает его целиком, включая terminal LF.
- `LineSink` закрывает каждую строку с признаком `closedByDelimiter` (перевод строки в потоке — true; хвост файла без delimiter'а — false; pending CR в EOF — true), и этот признак доезживает до `Emit`. `CanonicalContent` расширен полями `StartLine`/`EndLine` (фактически возвращённый диапазон, null для пустого выбора), `Truncated` (cap сработал: `captureFullText && end < total`; для range-запроса всегда false) и `HasMore` (`end < total`).
- `ReadFileResult` (`Protocol/Models/`) дополнен публичными полями `total_lines`, `start_line`, `end_line` (int?; `WhenWritingNull` опускает их для пустого выбора), `truncated`, `has_more`; сериализация — тот же source-generated `McpJsonContext`, фиксируется тестом `ReadResultSerializesThroughTheSourceGeneratedContextWithFidelityMetadata`. Описание tool'а (`ReadFileTool.Description`) документирует семантику текста и метаданные.
- `FileService.ResolveEffectiveMaxLines` отвергает `max_lines` без `allow_large_read=true` как аргументную ошибку (`ArgumentOutOfRangeException` → `-32602`), вместо молчаливого игнорирования. Guard-ы 1000/50000 и explicit range limit сохранены: полный read >1000 строк без opt-in и >50000 без явного `max_lines` — `resource_limit` после сканирования (FS-07 R1 шаг 5); range шире effective `max_lines` — `resource_limit` до чтения.
- Бюджет ответа для всех форм чтения (FS-07, уже в 1.8.0): `textLimit` = `MaterializationLimit` передаётся и в range, и в prefix; в 1.12.0 проверка `textLimit` в `Emit` считает разделитель по флагу «строка уже выбрана» **и единицу на закрывающий LF выбранной строки** (`closedByDelimiter`): переполнение только из-за этого LF отказывает уже в `Emit`, и исключение выходит из цикла чтения — хвост файла не дочитывается, потому что отказ `resource_limit` не несёт ни текста, ни hash (FS-07 R1/R8). Ложных отказов +1 не даёт: для промежуточной выбранной строки проверка не превышает финальной длины текста (последующие строки только добавляют), для последней выбранной совпадает с ней точно. Дописывание LF в `OnScanCompleted` сохранено с подчинённой перепроверкой лимита. Превышение — `resource_limit` во время чтения; покрыто кейсами `RangeOverTheResponseBudgetIsRefusedWhileItIsRead` (отказ range по телу строк; ранее отказ range по ответному бюджету прямо не проверялся) и `ClosingLfOverTheResponseBudgetStopsTheReadImmediately` (переполнение даёт только закрывающий LF: отказ у обеих форм — range и prefix `allow_large_read` — с ограничением прочитанных байт первым чанком).
- Документируемая коррекция наблюдаемого поведения: `text` диапазона/prefix теперь заканчивается `\n`, если тот существовал в файле. Agents должны брать exact snippet из исправленного ответа. Обновлённые вместе с реализацией Baseline-ассерты: FS-07 `FileByteBudgetIsNotBypassedByAMiddleLineRange` («bravo\n»), `EverySupportedEncodingMatchesTheSharedParser` («beta\n»), `WholeFileHashStreamsForAOneLineRangeOfALargeSyntheticFile` («line\n», включая прямой `ReadCanonicalAsync`), `PrefixCapTruncatesLikeTheAcceptedReference` («a\nb\n»), `AllowLargeReadDoesNotRaiseTheMaterializationBound` (длина range +2, полный текст с terminal LF, `canonicalChars = lineCount × (lineChars + 1)`); FS-09 `CrOnlyAndMixedEndingsNumberLinesLikeReadFile` («needle Привет\n»); FS-03 `ReadHashMatchesSharedParserForWholeFileAndLineRange` («beta\n»).

ReadFidelityTests: leading blank lines, trailing newline, empty-only content, range starting at empty line; max_lines prefix имеет total_lines/truncated/has_more и полный hash. Unicode и hash-control остаются baseline.

Добавить: empty file, no terminal LF, exact cap/cap+1, CRLF normalization, out-of-range, huge single line FS-07, max_lines без opt-in, invalid ranges и consistent DTO source generation/AOT.
