# FS-07: Ограничение ресурсов, cancellation и отзывчивый transport

Приоритет: P1. Источники: Program.Main, FileTextHelper, FileService, SearchTool, ListDirectoryTool.

Статус: выполнено.
Версия реализации: 1.8.0.

Документ состоит из трёх частей, и они не пересекаются по смыслу:

1. **Контракт** — нормативный источник истины. Только он определяет поведение; таблицы настроек и правил ниже обязательны целиком.
2. **Реализация** — где какое правило живёт в коде и какие тесты его удерживают.
3. **Журнал** — что нашло адверсариальное ревью и что из этого изменилось. Журнал описывает историю, не правила.

Если реализация расходится с контрактом, прав контракт, а расхождение — дефект, а не «так работает». Соблюдение одной таблицы настроек без таблицы правил не является соблюдением спеки: именно так и были пропущены находки ревью.

## Дефект

Лимит строк применяется после полного ReadToEnd и hash byte[]; огромная строка не ограничена. Main ждёт tool до чтения нового frame, поэтому ping/cancel задерживаются. Regex timeout не ограничивает traversal.

## Контракт

### Настройки

Все лимиты положительны, проверяются на startup; CLI `--name=value`:

| Настройка | Default | Тип и потолок | Назначение |
|---|---:|---|---|
| maxRequestBytes | 1048576 | Int64, 1…2^63−1 | UTF-8 байты одного frame (payload без терминатора строки) |
| maxFileBytes | 67108864 | Int64, 1…2^63−1 | байты одного текстового файла |
| maxLineChars | 262144 | Int32, 1…2147483647 | UTF-16 code units одной строки |
| maxResponseChars | 1048576 | Int64, 1…2^63−1 | UTF-16 code units payload до фрейминга **и** уже сериализованного frame (см. R5) |
| searchMaxFiles | 100000 | Int64, 1…2^63−1 | посещённые files |
| searchMaxDirectories | 10000 | Int64, 1…2^63−1 | посещённые directories |
| operationTimeoutMs | 30000 | Int64, 1…4294967294 | deadline одной операции tool |
| maxConcurrentReads | 4 | Int32, 1…2147483647 | одновременные read-only операции tool |

Отдельного CLI-лимита на число записей `list_directory` нет — это намерение, а не пробел: он ограничен бюджетом payload и производным от него потолком материализации (см. R7). Собственный лимит с курсором появится в B-03 (пагинация).

Верхняя граница `operationTimeoutMs` — не удобство, а предел платформенного таймера: `CancellationTokenSource.CancelAfter` отвергает большее значение. Принятое значение, которое нельзя запланировать, привело бы к тому, что запрос не получит ответа вообще, поэтому весь диапазон выше границы — ошибка запуска, включая `long.MaxValue` (он не означает «без дедлайна»).

Границы делятся на два вида, и это разные исходы. Исход зависит от операции, поэтому таблица называет и то, и другое:

| Настройка | Равно лимиту | Лимит+1: отказ | Лимит+1: усечение |
|---|---|---|---|
| maxRequestBytes | frame принят | frame отклонён как `-32600`, ничего не выполняется | — |
| maxFileBytes | файл читается/пишется | `read_file`, `create_file`, `replace_in_file`: отказ `resource_limit` (для записи — до commit) | `search`: skip файла, поиск продолжается |
| maxLineChars | строка принимается | `read_file`, запись: отказ `resource_limit` | `search`: skip файла, поиск продолжается |
| maxResponseChars | payload/кадр доставлен | `read_file` (полное чтение, range, prefix `allow_large_read`): отказ `resource_limit` | `search`, `list_directory`: усечение с причиной (R7), операция продолжает отвечать |
| searchMaxFiles / searchMaxDirectories | N-й визит выполняется | — | обход останавливается, `truncated=true` + `truncation_reason` (R4) |

Ключевое различие: у `read_file` бюджет ответа — **отказ**, а не усечение. Частичный текст без признака неполноты расходится с требованием полного hash (R8), а признака «неполнота по бюджету» эта операция не выражает. Для range и prefix `allow_large_read` действует то же правило, что и для полного чтения: выбранный текст обязан уложиться в бюджет, иначе отказ. Это сужает FS-10, где выбор был сформулирован только для полного чтения.

Оболочка ответа: `isError=true` с кодом в `content[0].text` — для `tools/call`. Прямые RPC удалены в FS-12 (1.13.0); до удаления их оболочка была иной (`-32001`, без `details`, R16) при том же коде.

Ошибка запуска: неизвестное имя, пустое значение, нечисловое значение, ноль, отрицательное, значение выше потолка, переполнение при разборе, дубликат. Исход — сообщение в stderr с префиксом `Startup failed:`, ненулевой exit code, пустой stdout.

### R0. Потолки рабочих буферов и памяти

Размеры внутренних буферов фиксированы контрактом, потому что именно они задают верхнюю границу памяти на chunk:

| Буфер | Значение | Где |
|---|---:|---|
| чтение файла | 4096 байт на chunk | потоковый декодер |
| чтение frame | 8192 байта на чтение stdin | `BoundedFrameReader` |
| запись файла | 65536 байт на chunk | атомарный writer |
| probe поиска | 512 байт | бинарный probe |

Потолок памяти операции — это буфер **плюс** всё, что операция вправе материализовать, включая текущую строку:

| Операция | Верхняя граница памяти |
|---|---|
| `read_file` | `min(maxResponseChars, maxLines × (maxLineChars + 1))` + `maxLineChars` + 4096 + буферы кодера |
| `search` | `maxResponseChars` (payload) + `maxLineChars` (текущая строка) + 4096 на текущий файл |
| `list_directory` | `min(maxResponseChars, entryCap × (maxLineChars + 1))` + 8192, где `entryCap = MaxResponseChars / 21 + 1` (целочисленное деление) |
| frame | `maxRequestBytes` + 8192 |
| запись | подготовленные байты результата (`≤ maxFileBytes`) + 65536 |

Слагаемое `maxLineChars` — это буфер текущей строки, и оно есть у **каждой** построчной операции. Пока строка не закончилась, читатель собирает её целиком и лишь потом сравнивает с бюджетом текста; поэтому при `maxResponseChars` меньше `maxLineChars` пик задаёт длина строки, а не бюджет ответа. Без этого слагаемого формула читалась бы как «операция не превышает бюджет», что неверно.

Ни одна строка не зависит от размера файла сверх `maxFileBytes`. Материализованный **выделенный текст** ограничен бюджетом ответа, поэтому при дефолтах доминирует он (1 048 576 code units), а буферы и текущая строка задают добавку фиксированного размера.

Диагностика `maxLineChars` от этих границ не страдает: проверка длины строки идёт **раньше** проверки бюджета текста — читатель отвергает строку длиннее `maxLineChars`, разбивая поток на строки, — поэтому строка сверх лимита всегда сообщается как `maxLineChars`, а не как бюджет ответа. Ранее здесь стоял потолок `max(maxLineChars + 1, …)`, и он был подгонкой под код: он допускал материализацию выделенного текста сверх бюджета ровно в том случае, когда бюджет меньше одной строки, что противоречит правилу «текст не накапливается сверх бюджета». Буфер текущей строки бюджетом и не ограничен — он ограничен `maxLineChars`, и это в формуле теперь сказано прямо, а не замаскировано.

### R1. Порядок применения лимитов

Для одной операции лимиты применяются в этом порядке, и первый сработавший определяет исход:

1. `maxRequestBytes` — на уровне кадра, до разбора JSON и до любого tool.
2. `maxFileBytes` — по длине файла, **до открытия, до чтения и до hash**.
3. `maxLineChars` — по строке.
4. `maxResponseChars` — по материализуемому тексту (во время чтения) и по готовому кадру (при записи).
5. Счётные guard'ы FS-10 (1000/50000 строк) — после сканирования, потому что для них нужен полный счёт строк; они не отключаются и не заменяются бюджетом ответа. Применяются они только к чтениям, дошедшим до конца: отказ на шагах 2–4 прекращает сканирование (R8), поэтому позже сработать уже не может.

Так выглядит разрешение конкуренции: **раньше по номеру — раньше по исходу**. После отказа на шаге 2, 3 или 4 клиент видит `resource_limit` с причиной того шага, на котором чтение остановилось, и guard'ы шага 5 в этом чтении уже не участвуют.

### R2. Отказ и skip — разные исходы, и они не взаимозаменяемы

| Операция | Превышен `maxFileBytes` / `maxLineChars` | Превышен `maxResponseChars` | Что видит клиент |
|---|---|---|---|
| `read_file`: полное чтение, range, prefix `allow_large_read` | отказ | отказ | `isError=true`, код `resource_limit` |
| `create_file`, `replace_in_file` (входной текст и результат) | отказ **до commit-точки FS-02** | не применимо (frame ограничивает транспорт) | `isError=true`, код `resource_limit`; файл не изменён и temp не создан |
| `search` | skip одного файла | усечение payload | skip: `skipped[]` с `reason=resource_limit`, `incomplete=true`; усечение: `truncation_reason` (R7); поиск продолжается |
| `list_directory` | не применимо (файлов не читает) | усечение payload | `truncated=true`, `truncation_reason=max_response_chars`; список остаётся |

Отказ для записи обязан быть **до** commit, а не после: проверка идёт на подготовленных байтах до создания temp-файла, потому что отказ после commit сообщал бы об ошибке для уже заменённого файла — ровно та неоднозначность, против которой существует граница commit FS-02.

Правило «это `resource_limit` до материализации» из FS-05 остаётся верным для отказов. Для поиска тот же код означает не отказ операции, а исключение файла: у поиска уже есть канал `skipped`/`incomplete` по FS-04, и терять все остальные совпадения из-за одного большого файла нельзя. Обязательное следствие: **любой skip по бюджету поднимает `incomplete=true`**, иначе пустой `matches` при `incomplete=false` читается как «совпадений нет».

### R3. Отмена, дедлайн и commit

Две причины отмены различаются по факту, а не по времени:

- **peer cancel по адресу** (`notifications/cancelled`, `$/cancelRequest`) — это `cancelled`: peer жив и ждёт ответ;
- **сработавший `operationTimeoutMs`** — это `resource_limit`, а для операции, умеющей вернуть частичный результат, — частичный результат;
- **EOF и shutdown** (закрытие stdin, смерть выходного канала) — не peer cancel и не дедлайн: ответ писать некому. Незавершённые операции отменяются, ответ не отправляется, процесс завершается штатно (R10). Отличие от peer cancel в том, что адресат ответа исчез, а не в причине отмены.

| Момент | peer cancel | сработал deadline |
|---|---|---|
| до commit-точки FS-02 | `isError=true`, `cancelled`; original не изменён | `isError=true`, `resource_limit`; original не изменён |
| после commit-точки FS-02 | success по FS-02 (запись durable) | success по FS-02 |
| `read_file` в любой момент | `isError=true`, `cancelled` | `isError=true`, `resource_limit` (частичного текста нет, см. R8) |
| `search` | `isError=true`, `cancelled` | `isError=false`, частичный результат, `truncation_reason=operation_timeout` |
| `list_directory` | `isError=true`, `cancelled` | `isError=true`, `resource_limit` |

`isError` указан явно в каждой клетке: успешный частичный результат существует ровно у одной операции, и это `search`. `list_directory` отдаёт частичный список только по бюджету ответа (R7), а не по дедлайну — при исчерпании времени уже собранный список не отдаётся, потому что R8 требует не выдавать неполноту без признака, а признак неполноты по времени эта операция не выражает.

Оба правила для записи обязательны одновременно: «отмена до commit — всегда `cancelled`» ограничено причиной peer, а дедлайн до commit — это `resource_limit`, а не `cancelled`. Различитель обязан переживать и continuation, и границу tool-задачи; проверка по прошедшему времени запрещена как недетерминированная.

### R4. Границы searchMaxFiles / searchMaxDirectories

- Считается **каждый визит**: каталог — когда его identity впервые добавлена в visited; файл — когда он прошёл маску и был бы прочитан.
- Корень считается **ровно один раз**: как каталог, если он каталог, и как файл, если он файл. Одновременно и тем и другим он быть не может, поэтому «двойной» визит корня невозможен по построению.
- Одна identity не считается дважды: повторный визит в ту же identity не расходует бюджет и попадает в skip как `already_visited`; каталог, уже учтённый как файл, повторно как каталог не считается, и наоборот.
- Граница включающая: N-й визит выполняется, (N+1)-й останавливает обход.
- Остановка обхода — это `truncated=true`, `incomplete=true` и `truncation_reason` = `search_max_files` или `search_max_directories`.

### R5. Единицы и двойное применение maxResponseChars

Единица для `maxResponseChars` — **UTF-16 code units** (то же, что `maxLineChars`); `maxRequestBytes` и `maxFileBytes` — байты UTF-8.

Бюджет применяется дважды, и это два разных бюджета с одной настройкой:

- **payload** — то, что tool отдаёт как `content[0].text`. Считается в code units текста. Отвечает tool: он обязан отдать валидный JSON и либо уложиться, либо сообщить причину усечения в самом payload.
- **frame** — уже сериализованный кадр `{"jsonrpc":…}`, включая экранирование. Считается в code units итоговой строки. Отвечает транспорт: он единственный, кто видит экранирование.

Экранирование может раздуть payload сверх бюджета уже после того, как tool честно уложился. Поэтому при замене кадра транспорт **обязан сохранить исходную причину**, и у него есть два места для этого: `details.truncation_reason` в конверте tool-ошибки и `error.data.truncation_reason` в JSON-RPC ошибке. Второе нужно потому, что причина переживает и минимальный кадр, и замену результата, у которого конверта `content` нет вовсе (`tools/list`), — а `-32001` у legacy-методов поля `details` не имеет по FS-05 и причину нести не может.

Причина переносится **только** если её значение входит в закрытое перечисление R7. Проверка по таблице, а не по форме токена: причина — публичная метадата, и значение вне словаря не должно попадать к клиенту даже если оно похоже на машинный токен.

### R6. Бюджет меньше любого корректного кадра

Спека требует и уложиться в лимит, и отдать целый JSON с тем же `id`. Одновременно это выполнимо не всегда: существует минимальный корректный кадр, и он имеет приоритет над лимитом.

- Если бюджет ниже минимального кадра, транспорт отдаёт минимальный кадр и **превышает бюджет**. Усечение JSON или отказ от ответа запрещены: непарсимый кадр хуже, чем кадр сверх бюджета.
- Минимальный кадр — JSON-RPC error, а не result: `code` = `-32603`, `message` = `Response exceeds maxResponseChars`, `id` сохраняется, `error.data.truncation_reason` несёт причину, если она была. Он не может выглядеть как успешный пустой `tools/list` или пустой `search`.
- Для `tools/call` замена сохраняет оболочку `content`/`isError=true` и код `resource_limit`, пока она укладывается; ниже этой границы применяется минимальный error-кадр, и причина переезжает в `error.data`.
- Для `tools/list` и прочих result-методов замена — тот же минимальный error-кадр; подделывать `-32603 «Internal error»` вместо сообщения о бюджете запрещено.
- Точные длины минимальных кадров зависят от длины `id` и не фиксируются контрактом; тесты измеряют их в прогоне.

**`-32603` здесь — не дефект.** FS-05 закрепляет этот код за непредвиденным сбоем (нейтральный `Internal error` + `correlationId`). Бюджетный `-32603` — другой случай того же кода: он ожидаем, ограничен, не логируется как дефект и **не** порождает `correlationId`. Отличить их клиент может по `message`: `Response exceeds maxResponseChars` — это бюджет, `Internal error` — дефект. Это пересечение зафиксировано и в FS-05.

### R7. Словарь truncation_reason

`truncation_reason` — публичная метадата с закрытым перечислением значений:

| Значение | Причина | Кто ставит |
|---|---|---|
| `search_max_files` | исчерпан `searchMaxFiles` | search |
| `search_max_directories` | исчерпан `searchMaxDirectories` | search |
| `max_response_chars` | payload не уложился в бюджет | search, list_directory, транспорт |
| `operation_timeout` | сработал `operationTimeoutMs` | search |

Перечисление закрыто, и это ровно те четыре значения, которые сервер может выдать. Новое значение — изменение контракта: требует версии, записи в этой таблице, включения в список допустимых значений транспорта и теста. Значение вне таблицы не переносится в метадату (R5) и не появляется в ответе.

Поле присутствует только когда усечение фактически произошло. Причины делятся на два класса:

- **Причины исхода** — почему операция остановилась: `operation_timeout`, `search_max_files`, `search_max_directories`. Первая сработавшая побеждает и **не перезаписывается**.
- **Причина выдачи** — почему payload не уложился: `max_response_chars`. Она применяется только когда операции ещё не назначена причина исхода (`reason ??= max_response_chars`).

Не «побеждает первая», а «первая не отменяется второй»: разница видна на search, который упёрся в дедлайн, а затем ещё и в бюджет payload. Клиент видит `operation_timeout`, потому что именно он объясняет неполноту; `max_response_chars` сообщил бы лишь, почему ответ короче, и подсказал бы сузить запрос, который уже был усечён по другой причине. Так это и реализовано в `SearchTool.SerializeMatches`, и зафиксировано тестами `ResponseBudgetTrimsMatchesAndReportsMaxResponseChars` (чистый поиск, усечённый бюджетом, сообщает `max_response_chars`) и `AnAlreadyTruncatedResultKeepsItsCauseWhenThePayloadIsTrimmed` (поиск, усечённый дедлайном, сохраняет `operation_timeout`).

`list_directory`: `truncated=true`, `truncation_reason=max_response_chars` добавляются только при отброшенных записях; при отсутствии усечения форма ответа побайтово прежняя. Записи предпочтительнее отчёта, пока выбор существует, но **пол — это отчёт вместе с причиной**, а не пустой объект: отчёт делает усечение машиночитаемым и содержит причину, которая переживёт замену кадра транспортом.

Общий пол для обоих инструментов — **отчёт с причиной**, и он не понижается: `{"truncated":true,"truncation_reason":"…"}`. Причина обязана оставаться в payload, потому что транспорт читает её именно оттуда, когда заменяет превысивший бюджет кадр; пол без причины оставил бы клиента со знанием «результат усечён», но без ответа «почему». Ранее пол понижался до `{"truncated":true}` при бюджете меньше отчёта — это была та же подгонка с другой стороны: обещание «причину сохранит транспорт» не выполнялось, потому что сохранять было нечего.

Потолок числа записей проверяется явно: `entryCap = (int)Math.Clamp(MaxResponseChars / MinEntryPayloadChars + 1, 1, int.MaxValue)`, где `MinEntryPayloadChars = 21`, а деление целочисленное. `+1` нужен потому, что последняя запись может не влезть в бюджет и быть отброшена при отрисовке — тогда усечение должно быть честно названо отчётом, а не проглочено. Делитель 21 — нижняя граница длины одного элемента payload (`{"name":"","type":""}` вместе с разделителем), поэтому потолок никогда не меньше того, что вообще может быть доставлено. **Числа всех записей в ответе нет**: чтобы его сообщить, пришлось бы дочитать каталог после остановки материализации, а единственная граница этого дочитывания — дедлайн, который по R3 уничтожает сам список. Частичный список говорит `truncated=true` и больше ничего; полный счёт — задача пагинации B-03, где счёт сам ограничен.

### R8. Что именно возвращается при отказе

- `read_file`: отказ, а не частичный текст. Кусок файла без признака неполноты расходится с FS-10, где hash всегда описывает полный нормализованный текст.
- `search`: частичный результат допустим, потому что `matches` по своей природе неполны и неполнота выражается явно (`truncated`, `incomplete`, `truncation_reason`).
- `list_directory`: частичный список допустим по той же причине, но только по бюджету ответа (R7), а не по дедлайну: признака неполноты по времени эта операция не имеет, а выдавать неполный список без признака запрещено.
- Отмена или дедлайн посередине чтения не отдают ни текст, ни hash: hash описывает полный файл, поэтому неполный hash хуже отсутствия ответа.
- **Хвост сканирования не читается.** Отказ во время сканирования прекращает чтение сразу, а не дочитывает файл. Прежняя формулировка требовала дочитать ради счётчика строк и hash, и это было противоречием: отказ `resource_limit` не несёт ни текста, ни hash, поэтому дочитывание ничего не улучшало — оно только жгло бюджет. Следствия: hash не «некуда положить», его просто не вычисляют; guard'ы строк 1000/50000 после сканирования применяются только к чтениям, которые дошли до конца, то есть к успешным — файл, отвергнутый по бюджету, отвергается по бюджету, и это единственный видимый клиенту код.
- Peer cancel в отвергнутом чтении не наблюдаем: решение уже принято, чтение прекращено, а ожидание в невидимом хвосте не является частью ответа.
- Счётчик строк — целое, материализация — то, что ограничивает бюджет; пока сканирование идёт, текст не накапливается сверх бюджета. Именно поэтому отказ по `maxResponseChars` возможен для файла меньше `maxFileBytes` и больше `maxResponseChars`, и именно поэтому он не обязан дочитываться.

### R9. `maxConcurrentReads`

- Лимит — на **одновременные вызовы read-only tools** (`read_file`, `search`, `list_directory`). Это не лимит внутреннего параллелизма и не лимит мутаций.
- Мутации (`create_file`, `replace_in_file`) в лимит не входят: их координирует FS-02 по identity файла. Читать файл, пока идёт mutation, можно, и наоборот: это регулируется режимом разделения FS-02/FS-04, а не этим лимитом.
- При занятых слотах вызывающий **ждёт**, а не получает отказ. Ожидание входит в `operationTimeoutMs` и прерывается как peer cancel, так и дедлайном.
- Слот снимается в `finally`, поэтому cancel и любая ошибка его не удерживают; ожидающий, отменённый до получения слота, слот не занимает.
- Разные requestId не блокируют друг друга сверх лимита.

### R10. Reader кадра вне бюджета операции

- `operationTimeoutMs` — дедлайн операции tool и не ограничивает чтение кадра.
- Frame читается до LF. Отбрасывание превысившего `maxRequestBytes` кадра ограничено бюджетом, но не временем; пока кадр не добран, ping и cancel не обрабатываются, потому что неизвестно, где кончается кадр.
- EOF при пустом буфере — чистый выход с кодом 0. EOF посреди кадра — кадр отбрасывается как неполный, процесс выходит с кодом 0. В обоих случаях ответа не пишется: `cancelled` требует живого peer'а, которому можно ответить (R3), а stdin уже закрыт. Падение reader'а — запись в диагностику и **ненулевой** исход, а не «чистый EOF»: молчаливый exit 0 на дефекте чтения запрещён. Незавершённые операции при EOF отменяются, и незакоммиченная запись не повреждает original (FS-02).

### R11. Cancel: детали

- Известны два имени: `notifications/cancelled` и `$/cancelRequest`; параметр — `requestId`.
- Неизвестный, уже отвеченный requestId, повторный cancel, cancel `initialize`/`ping`/`tools/list` — no-op без ответа. Ответ на notification не отправляется никогда.
- Cancel одного requestId не отменяет остальные: отмена адресная.
- Гонка «ответ уже отдан»: если кадр ответа записан, cancel его не изменяет и второго ответа не порождает. Один request — ровно один ответ.
- Неподдерживаемое peer notification ответа не получает.

### R12. Regex и порядок причин

- Секундный match timeout (`RegexMatchTimeoutException`) — уже принятое FS-05 правило: это `resource_limit` всего поиска.
- Побеждает **первая сработавшая причина**, и никакого общего правила поверх этого нет. Секундный match timeout не «всегда первый»: при `operationTimeoutMs` меньше 1000 мс дедлайн срабатывает раньше, и исход — partial result с `operation_timeout` (R3). Обратный случай тоже возможен: обход может занять почти весь бюджет, и тогда матч на патологическом паттерне успевает упереться в свою секунду раньше, чем в дедлайн. Оба исхода определяются тем, что сработало первым, а не настройкой.
- Если за секунду паттерн не уложился, обход каталогов прекращается целиком: `resource_limit`, а не partial result.
- Приоритет причин при одновременном срабатывании — R7: причина исхода не перезаписывается причиной выдачи.

### R13. Взаимодействие с retry FS-04

FS-04 оставляет отмену целой операции и взаимодействие со своим retry на FS-07, поэтому:

- Пауза retry (50/100 мс, общий потолок 1000 мс) входит в `operationTimeoutMs`.
- Peer cancel и сработавший дедлайн прерывают паузу немедленно.
- Наружу уходит классификация FS-07 (R3), а не последняя sharing violation: отменённое ожидание не превращается в `file_locked`. Это **заменяет** правило FS-04 «при исчерпании остатка deadline наружу идёт последняя sharing violation» для тех случаев, где причиной исчерпания был `operationTimeoutMs` или peer cancel; для собственного потолка retry (1000 мс) FS-04 сохраняет силу.
- Отменённое ожидание не создаёт и не теряет блокировку: `SharingRetry` не удерживает ресурсов между попытками.

### R14. Верхние границы и переполнение

- Потолки заданы в таблице настроек; значение выше потолка и переполнение при разборе — ошибка запуска.
- Внутреннее представление: `Int64` для байтовых бюджетов и счётчиков, `Int32` для `maxLineChars` и `maxConcurrentReads`. Значение, не представимое в объявленном типе, — ошибка запуска, а не усечение.

### R15. Двойное чтение и «range не отменяет cap»

`maxFileBytes` применяется по длине файла до чтения и не зависит от запрошенного диапазона. Формулировка «range не отменяет cap, поскольку hash нужен для всего файла» описывает **почему** range не освобождает от проверки, но не является разрешением прочитать и захешировать файл сверх лимита: файл сверх лимита отвергается до открытия.

Тот же лимит применяется к результату `create_file` / `replace_in_file` и к длине строки во входном тексте (R2): результат проверяется по подготовленным байтам до commit, поэтому отказ не оставляет ни изменённого файла, ни temp.

### R16. Legacy-методы до FS-12

FS-12 (1.13.0) удалил прямые RPC-методы: такой `method` — `-32601`, операция не выполняется, поэтому отдельной оболочки `-32001` больше нет. До удаления они вызывали тот же registered tool (лимиты, бюджет, коды и cancellation совпадали с `tools/call`), а оболочка оставалась принятой FS-01/FS-04 (`-32001` с `code` в `message` и **без** `details`) — тогда перенести `truncation_reason` в `details` для legacy-ответа было нельзя, и причина ехала в `error.data` (R5).

### Устойчивость прогона

3 из 3 последовательных прогонов `Status=Baseline` дали 307 passed / 0 failed. До этого прогон был нестабилен по трём причинам, и две из них — следствие самого FS-07, а не среды:

| Причина | Что это было | Исправление |

| Гонка чтения диагностики | логи с FS-07 пишутся из рабочих потоков, а тест FS-06 читал `StringWriter` без блокировки и падал в `StringBuilder.ToString` | потокобезопасный `StringWriter` (подкласс с блокировкой в `ToString`) — гонка была латентной и раньше, FS-07 сделала её вероятной |

## Журнал: что изменило адверсариальное ревью

Ревью подтвердило счётчики и нашло семь дефектов; каждый закрыт правилом выше и тестом, который использует production-дискриминатор, а не шов. До ревью матрица была зелёной при живых дефектах: она достигала дедлайна только через принудительный шов и проверяла бюджет ответа только выше размера собственной замены.

| Дефект | Правило | Что добавлено |
|---|---|---|
| Принятый `operationTimeoutMs` выше предела таймера: сервер **не отвечал ничем** и оставался жив | Настройки, R10 | startup-отказ, reader ожидается в `RunAsync` |
| Peer cancel возвращал успешный partial result с `operation_timeout` | R3 | `RequestDeadline` публикует токен таймера; дискриминатор только по нему |
| Дискриминатор отменял один и тот же токен для обеих причин | R3 | два токена: операция видит «стоп», публикуется только факт дедлайна |
| `CancellationToken` не имеет `==`: проверка идентичности сравнивала ссылки и была всегда ложной | R3 | сравнение токенов удалено, причина читается по состоянию ambient-токена |
| `deadlineFired` читался снимком `bool` после срабатывания таймера | R3 | причина передаётся как `Func<bool>` и вычисляется в catch-фильтре |
| Бюджет ответа не ограничивал свою замену; non-content результат давал фиктивный `-32603 «Internal error»` | R6 | повторное измерение замены, минимальный корректный error-кадр, `id` сохраняется |
| Полное чтение материализовало весь файл до отказа (650 МБ peak на 64 MiB) | R1, R5 | `textLimit` = `min(maxResponseChars, maxLines × (maxLineChars + 1))`, отказ во время чтения |
| `maxFileBytes`/`maxLineChars` не применялись к поиску | R2 | per-file skip с `resource_limit` и `incomplete=true` |
| Ошибка чтения кадров проглатывалась и давала «чистый EOF» | R10 | reader ожидается, падение логируется и даёт ненулевой исход |

Изменения контракта внесены **в сами спеки**, а не только объявлены здесь:

- **FS-05** (`05-tool-errors.md`): строка `cancelled` сужена — сработавший дедлайн это не `cancelled`, а `resource_limit`; EOF ответа не порождает. Строка `resource_limit` расширена триггерами `maxFileBytes`, `maxLineChars`, `operationTimeoutMs`. `details` получил третье поле `truncation_reason` (закрытое перечисление R7). Добавлен раздел о том, что `-32603` несёт два разных случая — предсказуемый бюджет (`Response exceeds maxResponseChars`, без correlation id, не в correlation path) и непредвиденный дефект (`Internal error` + correlation id).
- **FS-10** (`10-read-fidelity.md`): из альтернативы «bounded result с metadata или resource_limit» выбран `resource_limit`, причём для всех форм чтения, включая range и prefix. Зафиксирован порядок лимитов и то, что отказ **прекращает** сканирование: дочитывать файл незачем, потому что отказ не несёт ни текста, ни hash, а guard'ы 1000/50000 применяются только к чтению, дошедшему до конца.
- **FS-12** (`12-unified-api.md`): добавлен раздел «Состояние после FS-07» — расхождение реализаций устранено, прямые RPC-методы выполняют операцию, поэтому их KnownDefect-случаи падают до удаления методов в FS-12.
- **FS-04** (`04-file-locks.md`): retry-правило уточнено — при причине `operationTimeoutMs` или peer cancel наружу уходит классификация FS-07, «последняя sharing violation» сохраняется только для собственного потолка retry; объект search расширен `truncation_reason`, а skip по бюджету файла описан как часть `skipped`/`incomplete`.

## Журнал: столкновения внутри контракта

Правила, добавленные по итогам ревью, сначала противоречили друг другу. Каждое столкновение разрешено нормой, а не формулировкой:

| Столкновение | Решение |
|---|---|
| R3 требовал `resource_limit` для дедлайна `list_directory`, R8 разрешал частичный список, R7 его строил | R3 фиксирует: частичный результат по дедлайну есть только у `search`; `list_directory` усекается по бюджету ответа, а не по времени, потому что признака неполноты по времени у неё нет |
| R8 требовал дочитать файл ради счётчика строк и hash, одновременно отказывая во время чтения | норма развёрнута: отказ **прекращает** сканирование. Дочитывание ничего не улучшало — отказ не несёт ни текста, ни hash, — и только жгло бюджет. Guard'ы строк применяются лишь к чтению, дошедшему до конца; конкуренция с бюджетом разрешается номером шага R1 |
| R7 сначала говорил «первая причина побеждает», затем — «бюджет перезаписывает» | причины разделены на исход и выдачу; `max_response_chars` применяется только при отсутствии причины исхода. **Потребовало правки кода:** `SearchTool.SerializeMatches` перезаписывал причину всегда, теперь `reason ??= max_response_chars` |
| R7 называл полом отчёт, код возвращал `{}` при бюджете меньше отчёта | пол понижен до `{"truncated":true}`, но и это оказалось подгонкой: причина в таком поле отсутствует, а транспорт читает её именно из payload, поэтому обещание «причину сохранит транспорт» не выполнялось. **Итог:** пол — отчёт **вместе с причиной**, без понижения. **Потребовало правки кода** в обоих инструментах |
| R0 сначала повторял формулу кода `max(maxLineChars + 1, maxResponseChars)` и объяснял её диагностируемостью строки | порядок проверок этого не требует: строка отвергается по длине **раньше** бюджета текста. Формула заменена на `min(maxResponseChars, …)`, а `FileService.MaterializationLimit` перестал брать `max`. **Потребовало правки кода** |
| R0 объявлял, что ни одна операция не превышает бюджет, но не учитывал буфер текущей строки, который собирается целиком до сравнения с бюджетом | слагаемое `maxLineChars` внесено в потолки `read_file` и `search` явно, с оговоркой, что бюджетом оно не ограничено и ограничено `maxLineChars`. Иначе при бюджете меньше строки пик задавала бы строка, а формула читалась бы как обещание, которого код не даёт |
| R7 запрещал отбрасывать последнюю запись, R6 заменял превысивший бюджет кадр целиком — вместе это давало ответ без записей | R7 переформулирован: пол — отчёт без записей; записи предпочтительнее, пока выбор существует, но payload сверх бюджета транспорт заменит целиком, поэтому метод обязан укладываться |
| R5 запрещал терять причину, R6 отдавал `-32603` без неё, у `-32001` нет `details` | причина получила второе место: `error.data.truncation_reason`; поля `details` у legacy-оболочки для этого не требуются |
| `-32603` был одновременно бюджетным отказом и непредвиденным дефектом | разведены по `message` и по correlation id: бюджетный отказ ожидаем, ограничен и не идёт в correlation path. Зафиксировано и здесь, и в FS-05 |
| R12 утверждал, что секундный regex timeout побеждает всегда, а таблица допускает `operationTimeoutMs` от 1 мс | побеждает первая сработавшая причина; при бюджете меньше 1000 мс дедлайн опережает match timeout |
| R4 считал корень и каталогом, и файлом, затем запрещал двойной счёт | корень считается ровно один раз — тем, чем он является |

Дополнительно закрыты дыры: R7 требует, чтобы **числа всех записей** в ответе не было (досчёт каталога ограничен только дедлайном, который уничтожает список, — счёт переходит в B-03); R5 проверяет причину **по таблице R7**, а не по форме токена; R0 фиксирует потолки буферов и материализации, которых раньше в контракте не было.

Две правки предыдущего раунда изменили **код**, а не только текст; этот раунд добавил ещё две по той же причине — норма была написана против реализации: пол ответа без причины (обещание «причину сохранит транспорт» не выполнялось, потому что причина не попадала в payload) и потолок `read_file`, допускавший материализацию сверх бюджета ответа. Все четыре исправлены в коде, остальные закрытия — нормы и документы.
