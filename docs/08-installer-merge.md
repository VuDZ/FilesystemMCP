# FS-08: Установщик сохраняет конфигурацию пользователя

Приоритет: P1. Источник: install2opencode.ps1.

Статус: выполнено.

Версия реализации: **1.9.0**. Независимое адверсариальное ревью проведено: в первом раунде найдены 10 замечаний (1 major в исходной формулировке, 8 minor, 1 latent) плюс замечания к тестам; все они закрыты в коде и покрыты регрессионными случаями, счётчики и свойства перемерены после правок (см. «Ревью первого раунда»).

## Дефект

Write-OpenCodeConfig генерирует новый config и стирает existing model/mcp servers. Нет backup/merge/atomic commit. Отказ последующего AGENTS update оставляет partial install.

## Контракт

- При существующем opencode.json разобрать поддерживаемый строгий JSON, сохранить все unknown settings/servers, изменить только mcp.filesystem-mcp и добавить schema только если она отсутствует.
- Existing filesystem-mcp: обновить type/command, сохранить прочие параметры этого server. При JSONC/invalid JSON/необъектном mcp отказаться без изменения файла; поддержку JSONC вынести в backlog.
- Первый изменяющий запуск создаёт уникальный backup точных исходных bytes. Backup path сообщается пользователю. Повторный идентичный запуск не переписывает config и не создаёт лишний backup.
- Prepare/validate config и AGENTS до публикации. Temp write + atomic rename; если второй commit сорвался, восстановить первый из backup и сообщить recovery outcome. Не обещать crash-atomic transaction двух файлов: на restart должен быть понятный recovery path.
- BinaryPath обязан быть существующим файлом, WorkspacePath — директорией; LiteralPath для путей с Unicode/скобками. Значения сериализовать JSON API, не вставлять raw strings.
- Согласовать будущую настройку -AllowSymLinks с пользовательским override FS-01: boolean default true; явное false добавляет --allowSymLinks=false в command. На reinstall корректно убрать старый флаг при default true. Прямые outside absolute/../ пути остаются запрещены в обоих режимах. Реализовано в 1.9.0 (см. «CLI»).
- AGENTS существующие правила сохраняет, повторное добавление не дублирует раздел. Несовместимые типы узлов — явный отказ вместо overwrite.

## Реализация (1.9.0)

### Строгий JSON

`ConvertFrom-Json` не является строгим парсером: 5.1 и 7 принимают комментарии, одинарные кавычки, trailing comma, ведущие нули, а 5.1 ещё и молча берёт **последний** документ из потока вида `{"a":1} {"b":2}`. Поэтому скрипт сначала валидирует документ собственным рекурсивным descent-валидатором (`Test-StrictJson`), и только затем разбирает его `ConvertFrom-Json`. Валидатор требует: ровно один документ без trailing content, двойные кавычки, корректные escape-последовательности `\uXXXX`, отсутствие неэкранированных control characters, отсутствие trailing comma и ведущих нулей. Результат (merged document) тоже проходит валидацию перед записью.

`mcp` проверяется по **члену** объекта (`$Root.PSObject.Properties['mcp']`), а не по значению, полученному через helper: пустой JSON-массив возвращается из функции PowerShell как `$null` и иначе скрыл бы `"mcp": []` от проверки. Необъектный `mcp` (массив, строка, число, boolean) — отказ без единой записи. Явный `null` читается как «не задано» и перезаписывается объектом: null не выражает намерения, а отказ отверг бы конфигурацию, автор которой имел в виду «не настроено».

### Глубина вложенности

`ConvertTo-Json` при превышении `-Depth` не падает, а **молча** заменяет всё ниже лимита строкой (в 5.1 — без единого предупреждения, в 7 — только warning), и результат остаётся валидным JSON. Поэтому сериализация идёт с `-Depth 100` (потолок, который принимает Windows PowerShell 5.1), а перед записью выполняется проверка round-trip: число вложенных объектов и массивов в merged document и в его сериализованном виде обязано совпадать. Расхождение — отказ с объяснением, файл не изменяется. Иначе глубоко вложенная чужая настройка была бы потеряна, а установщик отчитался бы об успехе.

Практическая граница: до 99 уровней вложенности конфигурация проходит и сохраняется целиком на обоих shell'ах. На 5.1 `ConvertFrom-Json` глубже 100 уровней отказывает сам (`RecursionLimit exceeded`) и файл остаётся нетронутым; на 7 сериализация обрезается, и это ловит round-trip.

### Merge

- Порядок ключей сохраняется (`[ordered]`/`OrderedDictionary`): существующие члены остаются на своих местах и в своём порядке, меняются только их значения. `mcp` переписывается на своей позиции, `filesystem-mcp` — на своей среди соседних servers, `type` и `command` — на своих позициях внутри сервера. Новые члены (`$schema`, `mcp`, `type`, `command`) добавляются в конец, поэтому повторный запуск не переупорядочивает файл пользователя.
- Повторяющиеся члены объекта отвергаются на любой глубине: JSON-читатель оставляет только одно значение, поэтому установщик не может знать, какое из них имел в виду автор. Проверка обходит вложенные объекты и объекты внутри массивов; это отказ до записи, как и коллизия регистра.
- `$schema` добавляется только при отсутствии; существующее значение не перезаписывается.
- `filesystem-mcp` — installer владеет `type` и **префиксом** `command`: первые два аргумента всегда этот binary и этот workspace. Из прежнего `command` переносится только **полная** именованная опция (`--name=value`), кроме устаревшего `--allowSymLinks=false`; позиционные остатки и одиночный `--name`, значение которого было отдельным аргументом, отбрасываются. Позиционный остаток доходит до сервера как лишний позиционный аргумент, а опция без значения отвергается сервером при старте — исходная пара была отвергнута точно так же, поэтому сохранять половину её нет смысла. Следствие — повторный запуск сходится: третий запуск не даёт второй копии префикса. Прочие поля сервера (`env`, `enabled`, …) сохраняются.
- Члены читаются регистро-чувствительно. `type` и `command` обновляются **только** если они названы точно так; `Type` или `Command` — чужие настройки, они сохраняются. Если же наш член сталкивается с чужим по регистру (например `Type` при добавлении `type`), документ отвергается: PowerShell не может прочитать такой файл обратно, и запись потеряла бы настройку.
- Прочие mcp servers и все неизвестные top-level настройки сохраняются как есть.

### Backup и atomic write

- Backup создаётся только на изменяющем запуске, до записи config, рядом с ним: `opencode.json.filesystemmcp-backup-<UTC stamp>-<8 hex>.bak`. Содержимое — точные исходные bytes (побайтовое копирование, не ре-сериализация). Путь печатается в отчёте.
- Запуск, чей config уже совпадает с желаемым результатом, не пишет ничего и не создаёт backup. Совпадение проверяется побайтово, а не по разобранному дереву.
- Запись — temp-файл в том же каталоге, затем замена: для существующего файла `[System.IO.File]::Replace($temp, $Path, [NullString]::Value)` — атомарная подмена, при которой путь никогда не исчезает, поэтому читатель видит либо весь старый файл, либо весь новый. Третий аргумент обязан быть `[NullString]::Value`: PowerShell превращает `$null` и `''` в пустой **путь**, который `Replace` отвергает, а в .NET Framework (Windows PowerShell 5.1) нет перегрузки без backup path, поэтому этот sentinel — переносимый способ сказать «не сохранять backup». Для нового файла `Replace` неприменим, поэтому он переносится `[System.IO.File]::Move` без перезаписи. `Move-Item -Force` оставлен только как fallback для цели, которую процесс вправе писать, но не вправе удалять (ReplaceFile требует DELETE на цель): он сначала удаляет файл, поэтому используется лишь тогда, когда атомарный вызов недоступен. Temp-файлы называются `opencode.json.filesystemmcp-<guid>.tmp` и не остаются ни при успехе, ни при отказе; temp-файлы с чужим именем не удаляются.
- Read-only атрибут цели снимается перед заменой — установщик вызывается именно для того, чтобы установить/обновить конфигурацию, и отказ на read-only файле не помог бы пользователю. Заблокированный (без `FILE_SHARE_DELETE`) или запрещённый ACL файл по-прежнему приводит к отказу: bytes остаются исходными, backup не создаётся.

### Prepare, commit, recovery

Порядок: разбор существующего config → merge → подготовка AGENTS.md (чтение и вычисление новых bytes, включая отказ, если цель — директория) → backup → atomic commit config → atomic commit AGENTS.md.

- Отказ на чтении AGENTS.md (locked, deny-ACL, директория, отсутствующий sample) — это отказ **подготовки**: config не тронут, AGENTS не тронут, backup и temp не созданы, exit ≠ 0, `Recovery: config-unchanged`.
- Отказ на commit AGENTS.md (config уже опубликован) — config восстанавливается из backup побайтово, exit ≠ 0, `Recovery: restored-from-backup`. Если config только создавался (backup отсутствует), новый config удаляется, `Recovery: removed-new-config`. Если восстановление само не удалось — `Recovery: complete-failure` и в сообщении указан путь backup как явный recovery path.
- Если изменений в config нет, а AGENTS.md нужно опубликовать, пишется только AGENTS.md; при отказе config остаётся как был (`Recovery: config-unchanged`).
- Crash-atomic транзакция двух файлов не обещается: после прерывания recovery path — backup, напечатанный предыдущим запуском (он остаётся на диске и после успешного восстановления), плюс повторный запуск, который сходится к тому же результату. Это записано и в `.DESCRIPTION` скрипта.

### CLI

```
install2opencode.ps1 [-BinaryPath <file>] [-WorkspacePath <dir>] [-AllowSymLinks <bool>]
                     [-WhatIf] [-AsJson]
```

- `-AllowSymLinks` — тип `[string]`, а не `[bool]`: значение через пробел (`-AllowSymLinks false`) в PowerShell 5.1 и 7 приходит строкой и не биндится в `[bool]` (проверены восемь написаний). Принимаются `true`/`false` без учёта регистра и с `$`-префиксом (`$false`); невалидное значение отвергается до остальных проверок. Отсутствие параметра = true; явное `false` добавляет `--allowSymLinks=false`, а запуск по умолчанию убирает устаревший флаг из прежнего `command`. Прямые outside absolute/`../` пути остаются запрещены сервером в обоих режимах — эта опция их не разрешает.
- `-WhatIf` — подготовка, проверки и полный отчёт без единой записи: ни config, ни AGENTS.md, ни backup, ни temp; `AGENTS.md: skipped`.
- `-AsJson` — одна строка строгого JSON на stdout: `binary`, `workspace`, `config`, `agents`, `configAction` (`updated`/`unchanged`/`would-update`/`would-not-change`), `agentsAction` (`created`/`appended`/`unchanged`/`skipped`), `backup`, `backupCount`, `recovery` (`none`/`nothing-published`/`config-unchanged`/`restored-from-backup`/`removed-new-config`/`no-previous-config`/`complete-failure`), `whatIf` (режим запуска, а не результат: у отказа в сухом прогоне он тоже `true`), `allowSymLinks`; при отказе та же форма плюс `failed` и `message`. Ключи с путями опускаются до пустой строки, когда сохранять было нечего.
- Human-режим печатает строки `Binary:`, `Workspace:`, `Config:` (со словом-действием), `AGENTS.md:` (со статусом), `Backup:` (`none (nothing to preserve)`, когда сохранять было нечего), `Recovery:`, `allowSymLinks:`, а при `-WhatIf` — ещё `Mode:`.
- Скрипт **ASCII-only** по необходимости: Windows PowerShell 5.1 декодирует BOM-less `.ps1` как ANSI, поэтому не-ASCII исходный текст был бы испорчен до запуска. Дополнительно при перенаправленном stdout скрипт переключает `[Console]::OutputEncoding` на UTF-8, иначе 5.1 печатает кириллицу в OEM-кодировке и путь в отчёте выглядит как `?`.
- Значения путей попадают в JSON только через `ConvertTo-Json` (JSON API), а не конкатенацией строк.

### AGENTS.md

- Цель отсутствует → файл создаётся как sample verbatim (`TrimEnd()` + CRLF). Раздел `# FilesystemMCP Agent Rules` при создании **не** добавляется: этот заголовок маркирует именно добавленный раздел.
- Цель существует без маркера `# INITIALIZATION SEQUENCE: AI Agent Behavioral Rules` → прежнее содержимое сохраняется, ниже добавляется разделитель `---`, заголовок раздела и sample. Правила пользователя остаются дословно.
- Маркер уже есть → `unchanged`, файл не переписывается (повторный запуск побайтово идентичен, раздел не дублируется).
- Цель — директория → явный отказ, а не overwrite.

### Независимая верификация четвёртого раунда

Все четыре пункта C1–C4 проверены отдельным агентом с нуля, чёрным ящиком: для каждого пункта собиралась копия текущего скрипта с **одним** минимальным откатом, дефект воспроизводился на ней, затем тот же случай прогонялся на репозиторной ревизии. 143 проверки, 143 прохода, на обоих shell'ах; каждое «файл не тронут» подтверждено совпадением хеша, длины и mtime плюс отсутствием `.bak`/`.tmp`. Дополнительно найдены два поведения, не входившие в C1–C4; оба закрыты:

| # | Замечание | Исправление |
|---|---|---|
| D1 | Сбой между копированием backup и возвратом хука (например отказ на снятии read-only атрибута) оставлял **осиротевший** `.bak`: результат хука не присвоен, отчёт говорил `backup:""`, а следующий запуск добавлял второй backup — инвариант «есть `.bak` ⇔ этот запуск заменил файл» нарушался | `New-ConfigBackup` сам убирает свою копию, если не может довести её до возврата: backup либо возвращается вызывающему, либо удаляется до выхода из функции |
| D2 | Одиночный `--name`, значение которого было отдельным аргументом (`["--logDirectory","C:/logs"]`), переносился без значения; сервер такую команду отвергает при старте | Переносится только полная опция `--name=value`; одиночный флаг отбрасывается вместе со своим значением (исходная пара сервером тоже отвергалась, так что регрессии нет) |

Про `-WhatIf:$false`: на Windows PowerShell 5.1 `-File script.ps1 -WhatIf:$false` не биндится вообще (switch получает литерал `"$false"`) и запуск падает до тела скрипта — это ограничение `-File`, а не скрипта; отсутствие `-WhatIf` даёт те же не-сухие семантики.

### Швы и ограничения среды

- `FILESYSTEM_MCP_TEST_POWERSHELL` задаёт shell по умолчанию (по умолчанию Windows PowerShell 5.1 на Windows, `pwsh` на других OS). `PwshFactAttribute` один раз за процесс ищет `pwsh` в `PATH`, просит у него major-версию и **явно skip'ает** случаи, если PowerShell 7 недоступен: отсутствие shell'а — это skip с причиной, а не падение.
- `FILESYSTEM_MCP_TEST_INSTALLER` направляет ту же матрицу на другую ревизию скрипта (со своим `AGENTS.md.sample` рядом), как `FILESYSTEM_MCP_TEST_SERVER` уже выбирает binary. Без переменной поведение не меняется.
- Отказ по правам воспроизводится ACL/локом в тестовом хосте. Зависимость от прав аккаунта и sharing-семантики Windows помечена `[WindowsFact]`; на других OS такие случаи skip'аются с причиной.
- Проверка аргументов запуском самого binary удалена: сервер при валидных аргументах выходит молча, поэтому такой запуск ничего не доказывает, но создаёт свои log-файлы в пользовательском каталоге — то есть тест писал бы вне своего sandbox. Установщик проверяет типы путей (binary — файл, workspace — директория) и строгость JSON, а отвергнутую опцию сервер сообщает клиенту при первом запуске.
- FS-08 не реализует `allowedRoots`/B-17 и не меняет поведение FS-01: `-AllowSymLinks` только формирует `command`, прямые outside absolute/`../` маршруты остаются запрещены в обоих режимах.
